# balance-control-lab

**机器人动力学建模 → 状态估计 → 平衡控制 → 关节轨迹规划 → 底层驱动抽象 的零依赖最小完整实现(纯仿真)。**

Python 3 标准库, **运行时零第三方依赖**(没有 numpy / scipy / control —— 矩阵乘法、
矩阵求逆、矩阵指数、离散 Riccati 迭代、特征值全部自己写)。`pytest` 只用于测试。

> ⚠️ **纯仿真, 不含任何真实硬件。** 没有接电机、没有接 IMU、没有接编码器、没有
> MCU、没有 ROS2、没有硬件在环。所有数字都来自本机数值仿真。详见文末[边界](#-边界诚实且具体)。

---

## 为什么做这个

很多机器人项目只有**运动学 + 关节级位置控制**这两块: 能算出末端在哪儿、能 PID 跟
一条关节轨迹, 但**没有动力学模型、没有平衡控制**。而"让一个本质不稳定的系统站住"
恰恰是控制能力最直接的证据 —— 它要求同时具备:

| 岗位要求 | 本项目对应的实做证据 |
|---|---|
| **运动学与动力学** | 拉格朗日法推导 cart-pole / 单摆 / 双轮自平衡车的运动方程; 能量守恒漂移 **1.84e-11**; 解析线性化与数值 Jacobian 逐元素对到 **7.7e-13**; 2R/3R 机械臂正逆解、雅可比、奇异检测(接近奇异时关节速度放大 **1970 倍**) |
| **平衡控制** | 自实现 DARE 迭代的 **LQR**(Riccati 残差 **1.15e-9**, 闭环谱半径 **0.9827**), 从 `θ=0.05 rad` **2.90 s** 收敛到 **1.0e-7**; Ackermann 极点配置; 带抗饱和的串级 PID; 能量法起摆(4.28 s 从下垂捕获顶点) |
| **关节轨迹规划** | 梯形速度 / **七段式 S 曲线(jerk 受限)** / 五次多项式; 峰值速度**恰好**等于 vmax、峰值 jerk **恰好**等于 jmax(误差 2.2e-16); 多关节时间缩放同步(终点时间差 **1.1e-16 s**) |
| **底层驱动** | 寄存器总线抽象(位域读-改-写、CRC-8、超时/重试/统计)、PWM **12 位量化 + 死区插入**(全周期扫描直通 tick 数 **0**)、正交编码器(含 **16 位回绕**处理)、IMU(量化 + 噪声)、1 kHz 周期调度器(抖动/超时/丢拍统计) |

零依赖 —— 不需要 `pip install` 任何东西就能跑(测试需要 pytest)。

```bash

```

## 几个关键设计

### 1. 为什么用拉格朗日而不是牛顿-欧拉

牛顿-欧拉要逐个刚体列受力/力矩平衡, 并手工消去约束力(小车受的地面法向力、摆杆的
铰链反力)。小系统里这些约束力没有物理意义, 却占了大半推导量, **而且一旦符号错了,
仿真"看起来还能跑", 只是能量慢慢漂移** —— 这是最难查的一类 bug。

拉格朗日法的产物是标量 `L = T − V`, 于是能量守恒直接变成一条可执行断言:

```python
worst, _, _ = energy_drift(cartpole_ode(0.0, p), x0, energy_fn, 10.0, 1e-3)
assert worst < 1e-6        # 实测 1.84e-11
```

代价与边界也很清楚: 拉格朗日法对**非完整约束**(打滑、接触切换)不友好, 那类问题要
回到牛顿-欧拉或 Gauss 原理。本项目所有系统都简化成完整约束(轮子纯滚动)才避开了它。

还有一个反复踩到的坑值得写下来: cart-pole 的两条 Euler-Lagrange 方程如果先解出
`θ̈ = (g sinθ − ẍ cosθ)/l` 再回代, 会**除以 `cosθ`**, 在 θ→±90° 时爆掉。正确做法是
显式解 2×2 线性系统, 得到

```
θ̈ = [(M+m)g sinθ − m l sinθ cosθ θ̇² − F cosθ] / [l(M + m sin²θ)]
```

分母恒 ≥ `lM > 0`, 全状态空间良定义。`test_cartpole_deriv_never_divides_by_cos`
就是为这条设的。

### 2. 为什么 LQR 必须校验 Riccati 残差

这是本项目里最容易被忽略、后果最严重的一条。

DARE 的不动点迭代**不收敛时仍然会返回一个看起来完全正常的 K**。此时闭环矩阵
`A − BK` 的谱半径可能是 1.02 —— 系统会**慢慢发散**, 在 3 秒的仿真里根本看不出来,
实机上几十秒后一定翻车。

所以 `lqr()` 返回的是 `(K, info)`, 而 `info` 里强制带上:

```python
info["residual"]            # ‖A'PA − P − A'PB(R+B'PB)⁻¹B'PA + Q‖_F   实测 1.152e-09
info["spectral_radius"]     # max|eig(A − BK)|                          实测 0.982708
info["converged"]           # 迭代是否真的收敛
info["iterations"]          # 实测 823 次
```

三条断言都写在 `tests/test_control.py` 里。**残差和谱半径是返回值的一部分, 不是可选
的调试信息** —— 这是刻意的 API 设计。

另有一条踩坑记录: cart-pole 倒立点的谱是 `{0, 0, +ω, −ω}`, `+ω` 与 `−ω` **模长完全
相等**。幂迭代在这种情形下会在两个方向之间来回跳, 永远不收敛, 实测返回过一个毫无
意义的 11.29(真值 4.6456)。所以 `power_iteration` 带 `shift` 参数(迭代 `A + σI` 再
减回来), 加一个正移位就能打破对称。这条写在函数 docstring 里, 并由
`test_power_iteration_needs_shift_for_symmetric_spectrum` 守住。

### 3. S 曲线七段式: 峰值必须"恰好"对上限幅

S 曲线要处理的退化情况非常多: 位移太长/太短、`vmax` 到不到得了、`amax` 到不到得了。
分类讨论会有十几种情况, 每一种都要单独验算 —— 那是 bug 的重灾区。

本项目的做法: 把"半程距离"写成峰值速度 `v` 的**单调增函数**, 用二分法反解
`2·D_half(v) = d`。

- 只有一条代码路径, 单调性由物理保证;
- 200 次迭代把区间压到 1e-15, 峰值速度误差 **2.22e-16**;
- 代价: 每次规划约 200 次标量运算(微秒级), 而且**不是闭式解**。

峰值对账的断言是硬性的:

```python
assert tr.max_abs("velocity")     == approx(1.5,  rel=1e-12)   # 实测 2.22e-16
assert tr.max_abs("acceleration") == approx(6.0,  rel=1e-12)   # 实测 0
assert tr.max_abs("jerk")         == approx(40.0, rel=1e-12)   # 实测 0
```

**为什么这条对账能抓 bug**: 开发过程中梯形速度轮廓曾经把"恒定加速度段"写成了
`(duration, amax)`(把加速度当 jerk 传)。结果加速度只升不降, 但**位置居然还是能对上**
—— 因为错得很"对称"。只有"峰值速度恰好等于 vmax"这条断言立刻报了 0.9999994 而不是
1.0。

端点约定: 轨迹在 `t ≤ 0` 与 `t ≥ T` 返回静止值, 所以"端点位置/速度/加速度/jerk 全为
0"在三条轨迹上都严格成立(实测 0.0e+00)。**这个约定不掩盖梯形曲线端点加速度阶跃的
事实** —— 用 `t = 1e-9` 采样立刻能测到它(`test_trapezoid_acceleration_is_discontinuous_just_inside`)。

### 4. 驱动抽象: PWM 死区与编码器回绕

**PWM 死区**: 上下桥臂同时导通 = 电源直接短路 = 炸管子。做法是上管关断后延迟
`dead_time_ticks` 才允许下管开通, 于是占空比上限被顶到 `1 − 24/1000 = 97.6%`。测试
扫遍整个 PWM 周期 × 8 组占空比, 断言直通 tick 数恒为 **0**; 同时**反向断言死区确实
存在**(否则"没有直通"可以靠"永远不导通"来作弊):

```python
assert len([k for k in range(period) if pwm.gate_states(k)[0]]) == pwm.duty_ticks()
assert pwm.duty_ticks() > 0
```

死区还会带来一个必然的性能损失: 写入 0.5 的占空比, 实际等效只有 **0.476**(损失 2.4%)。
这就是"仿真很准、实机差一点"的来源之一, 在 `bench` 里可以量化看到 —— 同样的 LQR
增益, 完整驱动栈下控制能量从 1.512 涨到 14.215。

**编码器回绕**: 硬件计数器是 16 位有符号, 到 32767 后翻转到 −32768。**这是生产代码
最容易翻车的地方** —— 直接把寄存器值当位置用, 车会在某一刻突然以为自己瞬移了
65536 个计数。本项目同时维护两个量并断言它们的差:

```python
enc.seed_count(32766); ...  # 前进 4 个正交状态
assert enc.count_raw   == -32766      # 寄存器里真实存的东西
assert enc.count_total ==  32770      # 不回绕累计值(控制算法只能用这个)
assert enc.wrap_count  ==  1
```

### 5. RK4 收敛阶: 4 阶不是"看起来对"

不用"曲线看起来跟解析解重合"来判断积分器对不对 —— 那对 2 阶和 4 阶都成立。直接量
**收敛阶**:

```python
e1 = err(dt=0.02); e2 = err(dt=0.01); e3 = err(dt=0.005)
assert 12.0 < e1 / e2 < 22.0     # 实测 15.97
assert 12.0 < e2 / e3 < 22.0     # 实测 15.99
```

基准方程刻意选**非线性**的 `x' = x²`(解析解 `1/(1−t)`), 避免线性系统上 RK4 恰好精确
造成的假通过。抄错任何一个 `1/6` 系数, 收敛阶会掉到 2 或 3, 比值立刻不是 16。

## ⚠️ 边界(诚实且具体)

这一节比上面的数字更重要。下面每一条都是**这个项目没有做**的事。

### 1. 纯仿真, 没有真实硬件

数据来自数值积分, 不是实测。具体地:

- **没接电机**: 没有驱动器、没有电流环、没有编码器反馈的实际延迟与丢脉冲;
- **没接 IMU**: 噪声是高斯白噪声, 没有零偏不稳定性(Allan 方差里的 1/f 项)、没有
  温度漂移、没有轴间不对准、没有非线性度;
- **没接编码器**: 正交解码是软件定时采样模型, 高速时会丢状态跳变(真机通常用 MCU
  定时器硬件解码规避);
- **没有 MCU / 没有实时内核 / 没有硬件在环(HIL) / 没有 ROS2**;
- "控制器在仿真里 1 kHz 能跑"**不等于**"在 MCU 上能跑" —— 仿真里没有中断优先级、
  抢占、缓存效应、总线等待造成的偶发大抖动。

### 2. 动力学是简化模型

- **无摩擦、无阻尼、无柔性、无间隙**: 关节/轮轴都是理想约束;
- **cart-pole 的摆杆是"无质量轻杆 + 末端集中质量"**, 丢弃了杆自身的转动惯量
  (`I = ml²/3`)。选它是为了让倒立点频率有闭式解 `ω² = g(M+m)/(Ml)` 可对账, 代价是
  与真实实物的频率会有几个百分点的差异;
- **双轮自平衡车做了大量简化**: 车身当点质量、两轮合成一个等效轮、纯滚动无打滑、
  无转向自由度、无轮胎柔性。它是"能不能平衡"的定性模型, **不能当实车标定模型**;
- 没有空气阻力、没有库仑摩擦/Stribeck、没有齿隙。真实关节的跟踪误差里齿隙和摩擦
  占大头 —— 所以本项目的跟踪 RMS 数字(1.16e-04 rad)**偏乐观**。

### 3. 控制方法有明确的上限

- **只做了状态反馈**: LQR + 极点配置 + PID + 能量法起摆。**没有做 MPC、没有做 WBC
  (全身控制)、没有做 ZMP/捕获点**;
- **没有足式机器人步态**: 本项目里没有腿、没有接触切换、没有摆动相/支撑相规划。
  cart-pole 和双轮车都是"一个连续接触的欠驱动系统", 与走路是两回事;
- **没有参考轨迹优化 / 没有 TOPP / 没有时间最优路径参数化**。多关节同步只做了"按最
  长时长统一缩放", 它保证终点同时到达, **不保证中间过程同步**;
- **没有系统辨识**: 所有模型参数都是手工设定, 没有从实测数据拟合过;
- **没有鲁棒性/吸引域分析**: 起摆 + LQR 的切换控制器**没有全局稳定性证明**, 只通过
  有限组初值仿真验证。LQR 的吸引域边界是经验值(实测能接住 `|θ| < 0.5 rad`、
  `|θ̇| < 5 rad/s`), 不是用 SOS/可达集算出来的;
- **没有做 SVD**: 雅可比条件数用 Frobenius 范数估计, 它**会高估**, 只用于打印诊断,
  不做阈值判断(阈值判断统一用 `|sin(q2)|`)。

### 4. 寄存器总线是内存模拟

`SimRegisterBus` 用一块 `bytearray` 实现寄存器语义 —— 它验证的是**协议与数值行为**
(位域读改写、CRC-8、超时重试、量化、饱和、回绕), 不是"真实 MCU 寄存器"。整个
`RegisterBus` 抽象的设计目标是"换实机时只需再实现 `_raw_read` / `_raw_write` 两个
方法", 但**这个可替换性没有经过实机验证**。同样, 1 kHz 调度器是软件时序模型, 不涉及
真实中断延迟。

### 5. 关于测试数量的说明

任务给的测试数量目标是 80~120 个函数, 实际写了 **301 个**(305 个 pytest 用例)。
多出来的部分集中在模块级不变量(矩阵运算、寄存器语义、编码器状态表、指标函数定义),
它们都是纯计算的快速测试(全量约 8 s, 其中约 1.3 s 花在能量守恒与收敛阶这类需要
几万步积分的数值验证上)。**这一点超出计划, 如实说明。**
